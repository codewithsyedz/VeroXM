# RBAC & Tenant Model Recommendation: Role Management, Multi-Tenant SaaS, On-Premises, and Approval Workflows

**Prepared for:** VeroXM (mycms-nextjs-nodejs)
**Scope:** How to implement the Role Management screen (Super Admin / Tenant Admin / Editor / Developer / Viewer, tenant selector, impersonation, Team Members table), how to make VeroXM sellable both as multi-tenant SaaS and as a fully self-contained on-premises install, and how to add configurable content-approval workflows — all on top of the Keycloak + Department work already built in [`IDENTITY-PLATFORM-RECOMMENDATION.md`](./IDENTITY-PLATFORM-RECOMMENDATION.md)
**Status:** Recommendation — extensively implemented and live-verified since; see §11 for the full implementation log and the current status of every item below.

---

## 1. Executive summary

This document folds in two decisions confirmed since the first draft, plus what they imply:

- **On-premises deployments will be fully self-contained** — a customer's on-prem install runs its own complete stack (own Keycloak instance, own database, own containers), with no runtime dependency back on any VeroXM-hosted service. This turns out to simplify things considerably: an on-prem install is always exactly one tenant, so it needs none of the multi-tenant Keycloak modeling below — it's identical to what Slice 1 already built and shipped (§3.2).
- **Configurable approval workflows are scoped to content publishing only** — an Editor's draft content routes through one or more configurable approval steps, each requiring sign-off from a role/permission, before it goes live. Structural changes (schema edits, membership/role changes) are explicitly out of scope for the workflow engine itself, though the same role-gating machinery still governs who can make those changes directly (§5).

With those settled, the remaining open surface is: **how does the SaaS side model many tenants on shared infrastructure** (§3.3), and **what does the approval-workflow engine actually need to look like** (§6). Both are laid out below with a concrete recommendation, not left open — but both also have a smaller number of real sub-decisions still worth confirming explicitly (§10) before implementation starts.

The core structural insight worth stating up front: **because on-prem is always single-tenant, VeroXM only needs to build the multi-tenant Keycloak modeling once, for SaaS** — the on-prem deployment mode is the trivial, already-solved case of the same schema, not a second thing to design. One codebase, one `Tenant`/`Department`/`Project` schema, two ways of populating and running it.

## 3. The tenant model: resolved

### 3.1 What "tenant" means going forward

Per your steer: **VeroXM itself runs today as one organization/tenant, with its own Departments, configurable approval workflows, and role-based approval use cases underneath it.** That confirms the interpretation this document's first draft called "Interpretation B" (§3b in the prior draft): **`Tenant` is a new layer above `Department` — a customer/account boundary — and `Department` keeps meaning exactly what Slice 1 already built it to mean: an internal org unit *within* one tenant.**

Concretely:

```
Tenant  (a customer account — VeroXM itself is tenant #1 today)
  └─ Department  (Keycloak Organization, unchanged from Slice 1)
       └─ Project  (unchanged)
            └─ Content, Collections, API tokens  (unchanged)
```

`Tenant` needs to exist as a real row in the schema (a new top-level entity, `tenantId` threaded down through `Department`) even though today there is exactly one of them. That's the only schema change this section requires — everything below `Tenant` is already built.

### 3.2 Why on-premises resolves for free

Because the confirmed on-prem model is **fully self-contained — one dedicated Keycloak instance, one dedicated database, per customer, with no shared control plane** — an on-prem install is, by construction, always exactly one `Tenant`. There is nothing to switch between, so:

- **The tenant selector in the mockup simply doesn't render on-prem** — there is only ever one tenant to select.
- **Keycloak topology on-prem is exactly what Slice 1 already built**: one realm, one Organization per Department. No realm-per-tenant question, no Organization-vs-realm tradeoff — those questions only exist when *many* tenants share *one* Keycloak instance, which by definition never happens on-prem.
- **The only on-prem-specific work is packaging and first-boot provisioning** (§4), not tenant modeling.

This is why §1 calls on-prem "the trivial, already-solved case" — it's worth being explicit that no new authorization design is needed for it at all.

### 3.3 Keycloak topology for SaaS — where the real design decision lives

The harder case is the shared, multi-tenant SaaS deployment, where many `Tenant` rows (many customers, VeroXM's own account being the first of them) live on one Keycloak instance. Keycloak Organizations are flat — one Organization cannot contain another — so `Tenant → Department` can't be expressed as `Organization → Organization`. Two ways to get the two-level hierarchy, and this document recommends a **hybrid**, sized to how VeroXM's SaaS customer base is actually likely to look:

| Tenant tier | Keycloak modeling | Why |
|---|---|---|
| **Small/mid SaaS tenants (the common case)** | `Tenant` → Keycloak **Organization**; `Department` → a Keycloak **group nested inside that Organization**. | Organizations scale to hundreds-to-thousands per realm (identity doc §3.2), which is what most SaaS accounts need. This is the one place that reworks Slice 1's shipped `Department → Organization` mapping — for SaaS tenants only, Department moves one level down to a nested group. |
| **Large/enterprise SaaS tenants, and every on-premises install** | `Tenant` → a dedicated Keycloak **realm**; `Department` → Organization inside that realm, **exactly as Slice 1 already built it — zero rework**. | Realms are the strongest isolation Keycloak offers, appropriate for a large enterprise customer who wants (or contractually needs) hard separation, and realms only need to scale to "VeroXM's dozen-or-so largest accounts," not its whole SaaS base — well within the "dozens-to-~100" ceiling already flagged in the identity doc §3.2. On-prem is the degenerate case of this same tier: exactly one tenant, one realm, always. |

This means the Department→Organization work already shipped in Slice 1 is **not wasted or contradicted** by adopting the Tenant layer — it's the correct, final model for on-prem and for large SaaS accounts, and needs a small, well-scoped extension (Organization becomes the child of a Tenant-Organization via nested groups) only for the smaller/mid-tier SaaS bucket.

**Threshold for which tier a SaaS tenant gets — confirmed starting point:** a SaaS tenant moves from the shared-Organization tier to a dedicated realm once it has **more than 10 Departments** — the same tier every on-premises install already sits in by default (§3.2), so this is really "when does a SaaS customer start looking, structurally, like an on-prem-shaped account" rather than a new rule. A hard compliance requirement (a SOC 2 tenant-isolation attestation, HIPAA, FedRAMP, etc.) still moves a tenant to the dedicated-realm tier immediately regardless of Department count — that trigger doesn't wait for the count to be reached. A contract-value-based override, for accounts that are large in revenue but structurally simple (few Departments), is left open for now (§10) pending real SaaS customer data to calibrate against.

## 4. Deployment topology: SaaS and on-premises

One codebase, one schema, two ways of running it:

- **SaaS (hosted, multi-tenant):** one shared cluster (the deployment this repo's `docker-compose.yml` already resembles, scaled out), one Keycloak instance serving the hybrid topology in §3.3, many `Tenant` rows, VeroXM's own usage being tenant #1. Onboarding a new SaaS customer is a data operation (create a `Tenant` row, create its Organization or realm per the §3.3 threshold) — no redeploy.
- **On-premises (dedicated, single-tenant):** the customer runs the entire stack themselves — `keycloak`, `keycloak-db`, `db`, `api`, `web` (or whatever the production topology becomes) — inside their own network, with exactly one `Tenant` row auto-created on first boot. No call-home dependency for auth, licensing checks, or normal operation, per the confirmed "fully self-contained" requirement. This is the same `docker-compose.yml`-shaped stack Slice 1 already runs in dev, just handed to the customer to operate rather than run by VeroXM.
- **What has to be built, specifically for this mode split** (beyond the Tenant/Department schema work in §3):
  - A first-boot provisioning step that creates the single default `Tenant` (and realm/import, matching `docker/keycloak/import/mycms-dev-realm.json`'s existing seed-on-boot pattern) when running in on-prem mode — reusing the exact "seed via realm-export JSON on `docker compose up`" mechanism Slice 1 already built, just pointed at a production-shaped realm instead of a dev one.
  - A packaged, versioned release artifact the customer can actually deploy and upgrade (a versioned Docker Compose bundle, or a Helm chart if the target customers run Kubernetes) — this repo doesn't have a packaging/release story yet for anything, on-prem or otherwise, and it's a prerequisite for on-prem regardless of the RBAC work.
  - Licensing/entitlement enforcement that works with **no phone-home** — e.g. a signed license file the customer installs locally, checked against install limits (seats, projects) without a network call out, rather than a SaaS-style metered API check.
  - Explicit decisions on how a fully offline install applies security/dependency updates, and how support/telemetry (if any) is handled without an outbound connection by default — both flagged as open in §10 rather than assumed here, since they're product/support decisions as much as engineering ones.

## 5. Role vocabulary and permissions

§5.1–§5.3 are unchanged in substance from the first draft — reproduced here because the Tenant layer in §3 changes what "Tenant Admin" is scoped to, not how the five roles map onto the existing mechanism. §5.4–§5.8 are new: a concrete permission catalog and the advanced role use cases (Department-scoped admins, custom roles, a user holding different roles in different places at once, time-boxed elevation) that the five-role mockup implies but doesn't spell out on its own.

### 5.1 Role vocabulary → Keycloak / `model_has_roles` mapping

| Mockup role | Maps to | Notes |
|---|---|---|
| **Super Admin** | Existing global `super_admin` role, unchanged. | Bypasses every check in `RolesService.canAccess` today; stays global across every Tenant. |
| **Tenant Admin** | A new Tenant-scoped role, read from the Tenant's Organization/realm role claims (§3.3), following identity doc §3.3's "claims, not `model_has_roles` strings" recommendation. | Scope is now explicit per §3.1: the whole Tenant (every Department and Project under it), not just one Department — a materially bigger grant than any role `RolesService` expresses today. |
| **Editor** | The existing `editor{projectId}` grant, unchanged in meaning — full read/write on a Project's content, now also gated by the approval workflow in §6 where one is configured. | Already implemented; becomes claims-sourced per identity doc §3.3, same as Admin. |
| **Developer** | **Not a rung on the ladder — a different kind of grant.** Access to a Project's API collections/tokens (the Developer Module, identity doc §3.2a), modeled as a permission rather than a tier. | Requires the permission-based `RolesService` in §5.2 — forcing Developer onto the Admin/Editor ladder would misrepresent it. |
| **Viewer** | A genuine new read-only tier — `GET`-only access to a Project's content. | The one role here that needs a real new authorization primitive; today's lowest tier already implies write access. |

### 5.2 `RolesService` needs to become permission-based, not just claims-sourced

Identity doc §3.3 recommends swapping *where* roles come from (Keycloak claims vs. parsed `model_has_roles` strings) but keeps the same tiered `canAccess(tier)` shape. That swap alone doesn't cover Developer, which doesn't sit on the Admin/Editor ladder at all. Recommend evolving the guard pattern from `@RequireProjectRole('editor'|'admin'|'super_admin')` to an explicit permission check (e.g. `@RequirePermission('content:write')`, `@RequirePermission('api-tokens:manage')`, `@RequirePermission('content:approve')` — the last one needed by §6), with each of the five roles mapping to a fixed *set* of permissions. Additive to the existing `ProjectRoleGuard` shape, not a rewrite of it.

### 5.3 Team Members table and role assignment

Same standing gap flagged in identity doc §2/§3.5 ("no UI or API to grant a role" — still only via the legacy Laravel admin). Build the Role Management screen against Keycloak's Admin REST API (list Organization/Tenant members, assign/revoke roles), generalized from "manage one project's members" (identity doc §4 step 6) to "manage a tenant's members across every role." "Status/last active" maps to Keycloak's own session data via the Admin REST API, not a column VeroXM computes itself.

### 5.4 Permission catalog

The concrete set §5.2's permission-based `RolesService` checks against, and what each of the five default roles is a bundle of. This is the piece that makes Developer and Viewer (and the approval workflow's approver grant, §6) actually well-defined rather than hand-waved:

| Permission | What it gates | Super Admin | Tenant Admin | Editor | Developer | Viewer |
|---|---|:---:|:---:|:---:|:---:|:---:|
| `content:read` | View a Project's content | ✓ | ✓ | ✓ | ✓ | ✓ |
| `content:write` | Create/edit draft content | ✓ | ✓ | ✓ | — | — |
| `content:approve` | Sign off an approval step (§6) | ✓ | ✓ | — | — | — |
| `content:publish` | Move content from Draft (or a fully-approved workflow) to Published | ✓ | ✓ | ✓ * | — | — |
| `api-tokens:manage` | Create/revoke a Project's API collection tokens (identity doc §3.2a) | ✓ | ✓ | — | ✓ | — |
| `members:manage` | Add/remove Tenant or Department members, assign roles | ✓ | ✓ | — | — | — |
| `workflow:configure` | Create/edit an approval workflow (§6) | ✓ | ✓ | — | — | — |
| `department:manage` | Create/edit Departments within a Tenant | ✓ | ✓ † | — | — | — |
| `tenant:manage` | Create/edit Tenants, choose realm-vs-Organization tier (§3.3) | ✓ | — | — | — | — |
| `impersonate:user` | Impersonate another user (§7) | ✓ | ✓ ‡ | — | — | — |

\* `content:publish` for an Editor only fires directly when the Project/Department has **no** approval workflow configured (§6.1) — where one exists, Editor still needs to route through it like today's direct-publish path would otherwise allow.
† Department-scoped, not Tenant-wide — see §5.5.
‡ Scoped to the Tenant Admin's own Tenant only, and never against a Super Admin — per §7's impersonation rules.

This table is the starting bundle, not a hard ceiling — §5.6 covers letting a Tenant Admin compose narrower custom roles from the same catalog.

### 5.5 Department-scoped admin, not just Tenant-wide

§5.1 defines Tenant Admin as Tenant-wide by design (§3.1) — but a Tenant that's grown past a handful of Departments (the same shape of tenant that crosses the >10-Department threshold into its own realm, §3.3) will often want an admin scoped to **one Department**, without handing them `tenant:manage`, `department:manage` for every other Department, or the ability to see other Departments' membership at all. Recommend a second, narrower role — **Department Admin** — holding the same permission bundle as Tenant Admin (`members:manage`, `workflow:configure`, `content:*`) but scoped to a single Department's Organization/group rather than the whole Tenant. This is additive to the five-role mockup, not a replacement for Tenant Admin, and maps cleanly onto Keycloak: a role granted at the Organization (or nested-group, for the shared-tier SaaS case in §3.3) level instead of at the realm/Tenant level.

### 5.6 Custom, composable roles

The five default roles (plus Department Admin, §5.5) are fixed bundles of the permissions in §5.4 — but "advanced use cases for approvals like user roles" is best served by letting a Tenant Admin **compose a narrower custom role from the same catalog**, rather than being limited to the defaults. The clearest concrete need this solves: a designated **content approver** who should hold `content:approve` (and probably `content:read`) without also getting `content:write` or `members:manage` — i.e., someone who reviews and signs off but doesn't edit and isn't an admin. Recommend:

- Custom roles are named, Tenant-scoped (or Department-scoped, matching §5.5), and built from an explicit checklist of §5.4's permissions — not free-text, so every custom role stays expressible as a Keycloak client role with a fixed claim set.
- The five defaults (plus Department Admin) ship as non-deletable, pre-built examples of exactly this mechanism — implementation-wise, a "custom role" and a "default role" are the same underlying object; the defaults are just the ones VeroXM ships pre-configured.
- Only `members:manage`-holding roles (Tenant Admin, Department Admin) can create or edit custom roles — gate this with its own permission (`roles:configure`) rather than folding it into `members:manage`, since "who can assign an existing role to a person" and "who can invent a new role" are different levers worth separating.

### 5.7 One user, multiple roles across scopes at once

Nothing above requires a user to hold only one role. The existing `admin{projectId}`/`editor{projectId}` mechanism already allows a user to be Editor on one Project and hold no role at all on another (identity doc §2) — this continues to be true, and becomes more visible once Developer/Viewer/custom roles exist: a single person can be **Editor on Project A, Viewer on Project B, and hold a custom "Content Approver" role scoped to Department X's workflow**, all simultaneously, with the Team Members screen (§5.3) showing the union of their grants rather than one dropdown value. The mockup's single "role" dropdown per team member is a simplification worth flagging as such — the underlying model, and the screen once built, should let one member show multiple scoped role chips rather than force a single global choice.

### 5.8 Time-boxed / delegated elevated access

A common real request once approval workflows (§6) exist in practice: a backup approver covering for someone who's out, or a temporary elevation for a specific task, without a standing role change that someone has to remember to revert. Recommend, as a fast-follow rather than a first-slice requirement: an **expiring role grant** — same underlying role/permission assignment as any other, but carrying an expiry timestamp that a scheduled job (or Keycloak's own token/session expiry, where the grant is short-lived enough to rely on that alone) revokes automatically. This is explicitly not needed to satisfy the "content publishing only" approval scope in §6 — it's a refinement worth designing for, not blocking the first slice on.

## 6. Configurable approval workflows (content publishing)

Scoped, per your confirmation, to **content publishing only** — not schema/structural changes, which stay governed directly by the role/permission checks in §5 rather than a workflow engine.

### 6.1 What it needs to do

- A piece of `Content` moves through a small state machine: **Draft → Pending Approval → Published**, with **Rejected** (returning to Draft with feedback) as a branch off Pending Approval. This is additive to whatever state `Content` already tracks — it does not replace `Project.status`, which is a different, project-level concept.
- A Project (or, more likely, a Department — see §6.3) can configure **one or more approval steps**, each step naming the permission/role required to approve at that step (reusing §5.2's permission model — e.g. a step requiring `content:approve`, which Tenant Admin holds by default and which could also be granted narrowly to a non-admin "approver" without making them a full Tenant Admin).
- Steps are **ordered and sequential** for a first version — content only reaches Published after every configured step has signed off, in order. (A more advanced parallel/either-or approval graph is explicitly not recommended for a first slice — see §6.4.)
- If a Project/Department has **no workflow configured**, publishing behaves exactly as it does today — direct Editor publish, no approval gate. This preserves the "additive, not a breaking change" discipline used throughout this engagement (identity doc §7.2's pattern of "existing paths keep working, unmodified").

### 6.2 Data shape (described, not designed as DDL — matching this document's own "no code" convention)

- An **`ApprovalWorkflow`** configuration: which Project/Department it applies to, and its ordered list of steps.
- An **`ApprovalStep`** per workflow: order index, required permission/role.
- A per-content-item **`ContentApprovalRequest`**: which workflow instance it's going through, current step, and a history of who acted (approved/rejected), when, and with what comment — this is the audit trail a "configurable approval" feature is meaningless without, the same principle §7's impersonation-audit requirement applies to a different feature.
- This is new, additive schema — no existing table changes shape, matching the "hand-written, narrowly-scoped SQL migration" convention already established (`packages/db/sql/0001`–`0005`) rather than a broad `prisma db push`.

### 6.3 Where a workflow is configured: Project or Department?

Worth flagging explicitly rather than assuming: the mockup's "advanced use cases for approvals like user roles" suggests different content, or different Departments, may need different approval chains — which argues for configuring a workflow **per Department** (with an optional per-Project override for a Department that needs an exception), rather than only per-Project. This mirrors the existing `Department → Project` containment (identity doc §3.2) and avoids re-configuring the same workflow on every new Project inside a Department. Recommend Department-level as the default configuration point, with Project-level override as a fast-follow rather than a first-slice requirement — flagged as an open decision in §10 since it changes the `ApprovalWorkflow` shape in §6.2 slightly (needs both a `departmentId` and an optional `projectId`).

### 6.4 What to explicitly not build in a first version

- **No parallel or branching approval graphs** (e.g. "either the Department Admin or the Tenant Admin can approve step 2") — sequential, single-approver-per-step is enough to prove the concept and covers the stated "content publishing only" scope; branching logic is real complexity that should wait for a demonstrated need.
- **No workflow versioning** (changing a workflow's steps while content is mid-flight through the old version) — a first version can reasonably require in-flight approvals to finish under the workflow definition that existed when they started.
- **No cross-tenant or cross-department approval chains** — an approval step's required role is always scoped to the same Tenant/Department the content belongs to; this keeps the workflow engine from becoming a second place (besides §3) where tenant isolation has to be reasoned about.

## 7. Impersonation

A real, audited security feature, not a UI convenience.

- **Use Keycloak's built-in impersonation, don't build a custom one.** The Admin REST API's `POST /admin/realms/{realm}/users/{id}/impersonation` mints a session for the target user without VeroXM ever touching or resetting their password — the same "don't re-invent what Keycloak already does" principle the identity doc applies throughout.
- **Who can impersonate whom needs an explicit, narrow rule.** At minimum: only Super Admin, and a Tenant Admin only within their own Tenant (never across tenants — this is now a hard requirement per §3.1's confirmed Tenant boundary, not a hypothetical). Nobody should be able to impersonate a Super Admin, closing off a privilege-escalation path.
- **Every impersonation must be audited** — who impersonated whom, when, for how long, with the actor's real identity preserved in the log throughout. `packages/db/sql/0005_create_api_request_logs.sql` already established the "narrowly-scoped, hand-written SQL migration for a new logging table" convention; a dedicated `impersonation_audit_log` follows it rather than introducing a new one.
- **The impersonated session must be visibly marked as such** in the UI for its duration, and easy to end explicitly, distinct from a normal logout.
- **Scope the impersonated session to what the target user could themselves reach** — impersonation borrows the target's identity, never grants the impersonator anything extra.

## 8. Migration plan (phased)

Builds on the identity doc's own §4 plan (Keycloak + Department are Slice 1, already shipped):

1. **Add the `Tenant` layer to the schema** (§3.1) — additive, one row for VeroXM's own existing usage, nothing backfilled beyond that yet.
2. **Extend the role model** to the five-role, permission-based shape (§5.1–§5.2) plus the permission catalog (§5.4) — independent of everything else in this plan, can proceed in parallel with step 1. Department Admin (§5.5) and custom/composable roles (§5.6) are the natural next increment on top of this, before or alongside step 5 below; time-boxed elevation (§5.8) is a later fast-follow, not part of this step.
3. **Ship the on-premises packaging work** (§4) — first-boot single-`Tenant` provisioning, a versioned release artifact, offline licensing. This has no dependency on the SaaS-specific Keycloak topology in §3.3 at all, since on-prem only ever needs the realm-per-tenant tier — it can be built and validated before the SaaS multi-tenant Keycloak work is even finished.
4. **Build the SaaS multi-tenant Keycloak topology** (§3.3) — the hybrid Organization+nested-group (small/mid tenants) vs. dedicated-realm (large tenants) split, plus the threshold decision in §10 for which tenants get which.
5. **Build the Role Management screen** against the Keycloak Admin REST API (§5.3), generalized from the identity doc's planned "manage project members" screen.
6. **Build the approval-workflow engine** (§6) as new, additive schema and a new guard integration point on content publish — ship with Department-level configuration only, per §6.3's recommendation, before considering Project-level overrides.
7. **Build impersonation** (§7), with the audit table and UI banner shipped in the same slice as the impersonate button — never before it.
8. **Backfill real Tenants/Departments and cut over**, following the same "prove against test accounts first" discipline Slice 1 used before touching real data.

## 9. Alternatives considered

| Option | What you get | Trade-off |
|---|---|---|
| **Realm-per-tenant for every SaaS customer, no Organization tier** | Simplest single Keycloak concept everywhere (on-prem and SaaS both "one tenant, one realm") | Runs directly into the scale ceiling already flagged (realms degrade past dozens-to-~100) the moment VeroXM's SaaS base grows past its largest few accounts — not viable as the only SaaS model. |
| **Organization-per-tenant everywhere, including large accounts, no realm tier** | Scales to thousands of tenants on one realm, one modeling approach for all of SaaS | Denies large/enterprise SaaS customers the harder realm-level isolation they may contractually require, and doesn't reuse Slice 1's already-shipped Department→Organization mapping unchanged for anyone. |
| **Recommended: hybrid (§3.3)** — realm-per-tenant for on-prem and large SaaS accounts, Organization+nested-group for the rest | Reuses Slice 1's shipped mapping unchanged for on-prem and large accounts; scales correctly for the common small/mid SaaS case; gives large customers real isolation without forcing it (at realm-management cost) on everyone | Two Keycloak topologies to operate and reason about instead of one, and a threshold decision (§10) about which tenants land in which tier. |
| **Build a fully custom, VeroXM-specific approval-workflow engine unrelated to the role/permission model in §5** | Full flexibility over workflow shape | Duplicates authorization logic in two places (who can approve vs. who can edit), the same "two sources of truth" problem the identity doc's §3.3 already argues against for roles generally — recommend the workflow engine consume §5's permissions directly instead. |

## 10. Open decisions to confirm before implementation

- **The realm-vs-Organization threshold for SaaS tenants — mostly resolved (§3.3).** Confirmed starting point: >10 Departments moves a tenant to the dedicated-realm tier, and a hard compliance requirement moves it there immediately regardless of count. ### 11.2 Department-level isolation and management screen — second pass

Direct follow-up to the gap §11.1 flagged and to feedback on the Role Management screen: *"one department can't see another department's projects, and set access for department-wise project members with roles."* Two distinct fixes, both built this pass.

**1. Closed the correctness gap, not just the display one.** §11.1 only knew about a *display* gap — a Tenant/Department Admin's name not showing in a project's member list even though their access worked. Looking closer (this pass) found a deeper, functional gap underneath it: `ProjectsService.findAll()` and the pre-existing `ProjectRoleGuard`/inline `canAccess()` calls (`collections.service.ts`, `collection-fields.service.ts`) only ever read `adminProjectIds`/`editorProjectIds` — they had **zero awareness** of `tenantAdminTenantIds`/`departmentAdminDepartmentIds`. In practice this meant granting someone `department_admin` didn't actually let them see or open any project in their department, list its collections, or manage its content/tokens — only the one `PermissionGuard`-gated proof-of-concept route and the new Role Management screen resolved that scope at all.

Fixed in `apps/api/src/authz/roles.service.ts`'s `getUserRoles()`: after resolving the base role arrays, if the user holds any `tenantAdminTenantIds`/`departmentAdminDepartmentIds`, it now queries every non-deleted `Project` whose `departmentId` is in their Department scope OR whose `department.tenantId` is in their Tenant scope, and merges those project ids into `adminProjectIds` (deduplicated). Every existing caller — `ProjectRoleGuard`, `ProjectsService.findAll()`, both inline `canAccess()` sites — picks this up automatically, with no changes to any of them, since they all just read `roles.adminProjectIds` or call `canAccess()`. Purely additive: it can only add ids on top of what direct role grants already resolved, so it cannot narrow or change any previously-verified permission result (the `dept-admin`/`dept-editor` bundles confirmed live in §11 are unaffected).

This is also the mechanism behind the isolation the user asked for: a project with no Department (or a Department outside a user's Tenant/Department Admin scope) is simply never added to that user's `adminProjectIds`, so it never appears in their `/projects` list and every existing guard rejects direct access to it — no new "deny" logic was needed, just making the existing allow-list scope-aware.

### 11.3 Configurable approval workflows for content publishing (§6, §8 step 6)

The other half of what was asked for at the very start of this pass ("configurable approval workflows... Advance level use cases for approvals like user roles"), built after the Department isolation fix and screen above were verified live. Follows §6's design exactly: Department-level configuration (§6.3's recommended first-slice point — a Project-level override stays an explicitly deferred fast-follow), sequential single-approver-per-step (§6.1/§6.4 — no parallel/branching graphs, no workflow versioning), additive by default (a Department with no workflow configured publishes exactly as it always has — direct Editor publish, no gate).

**One real design gap found and fixed while building this, not just implementing §6 as written:** §6.1 says each step names "the permission/role required to approve," and §5.2's permission model was the obvious thing to reuse — until checking `apps/api/src/authz/permissions.ts` showed `content:approve` is granted identically to `admin`, `department_admin`, `tenant_admin`, *and* `super_admin`. A permission alone can't express "an Admin approves step 1, a Department Admin gives final sign-off at step 2" — the exact "advanced use cases... like user roles" scenario asked for — since all of those tiers hold the same permission. Steps are keyed on a **role kind** instead (`admin` | `department_admin` | `tenant_admin`; Super Admin always satisfies any step, so it's deliberately not a stored choice), checked via a new `RolesService.satisfiesRoleKind()`.

That in turn surfaced a second, subtler issue: `UserRoles.adminProjectIds` is the *effective* list since §11.2's isolation fix — it already includes projects a Department/Tenant Admin only reaches through inherited scope, not just direct `admin{id}` grants. Checking `adminProjectIds` for an `'admin'`-kind step would let a Department Admin satisfy it too, collapsing the very distinction this feature needs. Fixed by adding `UserRoles.directAdminProjectIds` — captured before §11.2's expansion runs — and `satisfiesRoleKind`'s `'admin'` branch reads that instead. Nothing else changes: every existing caller of `adminProjectIds` (§11.2's fix, `ProjectRoleGuard`, `ProjectsService.findAll()`) is untouched.

### 11.4 Developer/Viewer project roles — closing the access-layer gap (§8 step 5 follow-up)

§5.2/§11.1's permission catalog already defined Developer (`content:read`, `api-tokens:manage`) and Viewer (`content:read`) correctly, and `RolesService.getPermissionsForProject()` already resolved a `developer{id}`/`viewer{id}` grant into the right permission set — but nothing in the actual request path ever let either role holder reach a project at all. Grepping for `developerProjectIds`/`viewerProjectIds` outside `roles.service.ts` turned up zero other usages: every read route a project member needs (`GET /projects`, `GET /projects/:id`, both Collections routes, Content's list/detail/approval-status routes) was still gated `'editor'`-tier-or-above, and `ApiTokensController` — the one capability that actually defines the Developer role — was `'admin'`-tier only. A fresh Developer or Viewer grant was real in the database and correctly resolved by the permission layer, but functionally inert.

**Fix:** a new `'viewer'` tier was added to `ProjectRoleGuard`/`RolesService.canAccess()` (`admin{id}` OR `editor{id}` OR `developer{id}` OR `viewer{id}` — i.e. "any project-scoped role at all"), applied only to genuinely read-only GET routes: `ProjectsController.findOne`, `ProjectsService.findAll()`'s own `accessibleIds` computation, both `CollectionsController` read routes, and `ContentController`'s list/detail/approval-status routes. Every mutating route (create/update/publish/unpublish/approve/reject/trash/restore/remove) was deliberately left at `'editor'` or `'admin'` — `'viewer'` was never widened onto anything that writes. `ApiTokensController` was switched from a role-tier guard to `@RequirePermission('api-tokens:manage')` (the `PermissionGuard` pattern `RoleManagementController`/`ApprovalWorkflowsController` already use), since Developer's access to it is permission-shaped, not tier-shaped.

**A second real gap found only by testing live, not by re-reading the diff:** after the fix above compiled clean and a fresh `viewer{id}` grant still didn't make its project appear in `/projects`, the actual cause turned out to be a completely separate controller — `apps/api/src/content/project-content.controller.ts`'s `ProjectContentController`, mapped at `GET /projects/:projectId/content` (the project-wide, non-collection-scoped entry list apps/web's Content page actually calls) — which lives in its own file, separate from `ContentController`, and was missed in the original pass entirely. It was still `'editor'`-tier; fixed the same way, to `'viewer'`.

**Infra footgun hit repeatedly while chasing the above, worth flagging on its own:** the api container's `nest start --watch` was not actually applying code changes — not just across a plain `docker compose restart api`, but even on its own file-triggered rebuild. Every attempt logged `Error: listen EADDRINUSE: address already in use :::4000` and crashed, leaving whatever process was already bound to port 4000 as the only thing serving traffic — so several rounds of "compiles clean, still shows old behavior live" during this slice were this, not a code bug. The only reliable recovery found was a full recreate (`docker compose kill api && docker compose up -d --force-recreate api`), which frees the port because the whole container (and every process in it) is torn down first.

**Two follow-up fix attempts, both tried live and both confirmed NOT to resolve it** (kept anyway — harmless, and each is independently good practice):
- `init: true` on the `api` service (real PID 1 process reaping/signal forwarding via the Docker Engine's built-in tini) — the theory being `npm run dev:api` as PID 1 wasn't forwarding signals to nest's child process cleanly. Confirmed live: still crashes with the identical `EADDRINUSE` on the very next rebuild after this was added.
- `TSC_WATCHFILE`/`TSC_WATCHDIRECTORY: DynamicPriorityPolling` env vars on `api` — the theory being `tsc --watch`'s native fs-event watching double-fires on Docker Desktop for Mac's bind mounts (a documented failure mode with a documented fix). Also confirmed live: still crashes the same way.

Since the crash reproduces identically regardless of *what* triggers the rebuild (docker restart, native fs watch, polling watch) and regardless of *how* PID 1 handles signals, the actual root cause is most likely inside `nest start --watch` (`@nestjs/cli`)'s own child-process respawn logic racing — spawning the new listener before the previous one has actually released the port — which neither of the above addresses. A real fix would likely mean replacing `nest start --watch` with a process manager that has more robust respawn semantics (e.g. `tsc --watch` piped into `nodemon --delay`, watching the compiled `dist/` output), which is a more invasive change to the dev workflow than this pass's scope justified. **Standing workaround, proven reliable every time this pass:** after any `apps/api` source change, force-recreate rather than trust the watcher or a plain restart:

```
docker compose kill api
docker compose up -d --force-recreate api
```

### 11.6 Project-level approval-workflow override (§6.3/§11.3's flagged fast-follow)

§6.3 recommended Department as the first-slice configuration point for an approval workflow and explicitly deferred a narrower Project-level override. Built here: a Project can configure its **own** set of approval steps that **fully replaces** its Department's workflow for that project (never merges with it) — and removing the override falls back to the Department's own workflow exactly as if the override had never existed, with no separate "no gate" state to track.

**Schema:** widened the same `approval_workflows` table (0007) rather than adding a parallel one — `department_id` is now nullable, and a new nullable/unique `project_id` column scopes a row to a Project instead. Exactly one of the two is ever set; enforced at the application layer (`ApprovalWorkflowsService`'s create paths), not a DB `CHECK` constraint, matching this codebase's existing precedent for cross-field invariants (e.g. `ContentService.resolvePublishIntent`'s state machine). `project_id` deliberately has no real FK against `projects`, the same convention every other `project_id` column in this schema already follows (0004, 0005, 0007). `ApprovalStep`/`ContentApprovalRequest`/`ContentApprovalAction` are untouched — a step just names a required role kind regardless of whether its workflow is department- or project-scoped, and the approve/reject/audit pipeline already operates purely in terms of `workflow_id`.

**Authorization — deliberately wider than the Department-level split.** Viewing and configuring a project's override are the *same* permission check here (unlike the Department-level panel's view-vs-configure split): Super Admin, Tenant Admin of the project's department's tenant, or **Department Admin of the project's own department** can see and edit it. A project with no department at all has no such scope to check against, so only Super Admin can see or touch its override. A plain project-level `admin`/`editor` role holder — even a Project Admin — is deliberately *not* included; this is Department/Tenant/Super Admin territory, the same authority that already configures the Department's own workflow, not a project-management permission.

**Resolution order** (`ContentService.getActiveWorkflow`): a project's own override, if one exists, is looked up first and used as-is — full replacement, never merged with the Department's steps. Only when no project-level row exists does it fall through to the Department's own workflow lookup. This is also what makes "remove the override" a free fallback: deleting the override row just means the first lookup finds nothing next time, with zero extra state to track.

**Frontend:** a new `ProjectApprovalWorkflowPanel.tsx` on the existing project Members page — deliberately a near-duplicate of the Department-level `ApprovalWorkflowPanel.tsx` rather than a shared component (different scope, different server actions, and no view/configure split to parameterize) — with the same ordered-step, full-replace-on-save UX. The Members page's own fetch for it (`getProjectApprovalWorkflow`) is the one fetch on that page that must **not** throw on a non-OK response: most project members are plain Editors/Developers/Viewers, so a 403 here is the ordinary case, not a failure. It distinguishes `undefined` ("not authorized — hide the panel entirely") from `null` ("authorized, no override configured — the project inherits its department's workflow") rather than collapsing both into one state.

### 11.7 Keycloak claims wiring for Tenant Admin / Department Admin (§8 step 4)

§3.3 (in `IDENTITY-PLATFORM-RECOMMENDATION.md`) flagged that once Keycloak is the real identity source, `tenant_admin`/`department_admin` should be read from its claims rather than left as legacy-only strings. Built here: a Keycloak realm role named `department_admin{departmentId}` or `tenant_admin{tenantId}` (identical shape to the existing `model_has_roles` convention) is synced into that same legacy table the moment its holder logs in via Keycloak — no other code changes anywhere else in the authorization stack.

**Design.** `RolesService.getUserRoles(userId)` has roughly 19 call sites across the API, every one of them working from nothing but a numeric legacy user id — none has any notion of "the current JWT payload" to thread a claims object through. Rather than change that signature everywhere, `apps/web/src/lib/auth.ts`'s `jwt` callback — which already resolves a Keycloak profile to a legacy user by email on every login — now also calls a new `syncKeycloakRoleClaims(legacyUserId, accessToken)` right after that resolution. It decodes the access token's `realm_access.roles` (plain `jwt.decode()`, not signature-verified `jwtVerify` — deliberately: this token is the direct result of this same server's own token-endpoint exchange with Keycloak moments earlier, not a bearer token from an untrusted caller, the same trust level the callback's existing `profile.email`/`sub` resolution already relies on), filters for names matching `/^(department_admin|tenant_admin)(\d+)$/`, and for each match upserts a `Role` + `ModelHasRole` row — the exact same Prisma upsert shape `DepartmentsService.grantDepartmentAdmin` already uses to grant these roles by hand. `RolesService` and every one of its 19 call sites are completely unchanged; this is purely an additional way rows land in a table they already read.

Deliberately **additive-only**: the sync only ever creates a row, never deletes one. `model_has_roles` has no column distinguishing a Keycloak-derived grant from a manually-granted one, so a reconciling/destructive sync risked silently revoking a manual grant the next time that person logged in with a token that didn't (yet, or ever) carry the matching realm role. Revocation still goes through the existing UI — `DepartmentAdminsPanel` for `department_admin`; there is still no revoke UI for `tenant_admin` (the same gap already flagged in §11.1/§11.2, unchanged by this work).

**Built:**
- `apps/web/src/lib/auth.ts` — `KC_ROLE_PATTERN`, `syncKeycloakRoleClaims`, and the call site inside the `jwt` callback's Keycloak branch.
- `docker/keycloak/setup-tenant-department-admin-roles.mjs` (new) — companion to the existing `setup-department.mjs`; idempotently creates the two realm roles and assigns them to `dept-admin`/`dept-editor` (mirroring their existing legacy grants — `department_admin1` and `tenant_admin1` respectively — so the two paths land on the identical role for comparison), defensively checks the `mycms-web` client has the built-in `roles` client scope assigned (the realm-export JSON doesn't pin `defaultClientScopes` explicitly), and finishes with a direct-grant smoke test that decodes a fresh token per user and confirms the expected role is present in `realm_access.roles` — so a Keycloak-side config gap surfaces immediately instead of as a confusing "sync did nothing" later. Wired up as `npm run keycloak:setup-admin-roles`.

Revoked `dept-admin@example.test`'s `department_admin1` grant via the Department Admins panel on `/departments/1`, and confirmed the loss of access: impersonating `dept-admin` afterward, `/departments/1` returned a 403 ("Departments API responded 403") and the workflow-override panel on `/projects/17/members` was gone.

### 11.8 Approval notifications — nav-bar "awaiting your approval" bell

§11.3 flagged the one gap left once Approve/Reject visibility itself was closed: "no notification when a request needs your approval — an approver has to open the item to see it's waiting." Built here: a bell in the top nav, visible from anywhere in the app, showing a live count and a dropdown of every content item currently awaiting the signed-in user's own approval action, across every project and department they have access to — not just the one they happen to be looking at.

**Backend.** A new `ContentService.getPendingApprovalsForUser(userId)`, exposed as its own top-level `GET /approvals/pending` (`MyApprovalsController`, `@UseGuards(JwtAuthGuard)` only — deliberately not nested under `ContentController`'s `projects/:projectId/...` path or gated by `ProjectRoleGuard`, since this answers "what's waiting on me, across every project" rather than anything scoped to one; mirrors `DepartmentsController`'s existing precedent for a JWT-only route that resolves its own authorization internally). It fetches every `status: 'pending'` request once (joined to its workflow/steps and its content's collection/project/department — two queries total, no per-request query), then keeps only the ones whose current step this user actually satisfies, reusing the exact same `satisfiesRoleKind` check `approveContent`/`rejectContent` themselves enforce — so nothing surfaced here could ever 403 if acted on. Each item's title is resolved the same `title`/`name`-field-or-first-field convention `ContentService.list()` already established, so the bell shows something recognizable rather than a bare content id.

**Frontend.** `ApprovalsBell.tsx`, rendered from `TopNav.tsx` — polls `getMyPendingApprovals()` (a small server action in `apps/web/src/app/(dashboard)/approvals-actions.ts`, its own `apiFetch` copy rather than importing another feature's, matching this app's per-feature-actions-file convention) every 30 seconds and on mount, showing a count badge and a click-to-open dropdown linking each item straight to its content edit page. No push/webhook/email infrastructure exists anywhere in this stack, so polling is deliberately the simplest thing that surfaces a waiting request without the user needing to remember to go look; a real deployment with a meaningfully sized approval queue would want to revisit this (a shared SWR/React Query layer, or a real push channel) rather than every nav render owning its own interval.

**A real gap this surfaced, and fixed before calling it done:** `ContentService.trash()` only ever soft-deletes the `Content`/`ContentMeta` rows — it never touches an in-flight `ContentApprovalRequest`. Nothing before this feature ever looked at "every pending request system-wide," so a trashed item with an open request sat unnoticed; the bell would have kept surfacing it as a ghost notification pointing at content nobody could act on anymore, live-verified by trashing a real test entry with a pending request still open. Fixed by scoping the query to `content: { deletedAt: null }` — excluded exactly like every other list in this file already excludes trashed rows from its default view. Left as a known, narrower gap: a *rejected or withdrawn* request is already excluded (only `status: 'pending'` is queried), but nothing here re-examines the workflow itself changing shape after a request was submitted against it — not a new gap this feature introduced, since `getApprovalStatus`/`approveContent` already resolve `currentStepOrder` against whatever the workflow's current steps are at read time.

3. Impersonating `dept-editor@example.test`: the bell **also** showed it. ### 11.9 Automated test coverage for the RBAC core

Every check in this document up to here was verified by hand -- log in as some user, click through the app, read the response. That's real verification, but it doesn't survive the next unrelated change to `roles.service.ts` or `content.service.ts`. This section adds the first automated coverage for this engagement's authorization surface, in three passes. The first covered the read side: `apps/api/src/authz/roles.service.spec.ts` (11 cases) and `apps/api/src/content/content.service.spec.ts` (8 cases, at the time -- `getPendingApprovalsForUser` only). The second pass broadened this to the write side and to the guards every route actually depends on: `content.service.spec.ts` grew 10 more cases covering `approveContent`/`rejectContent`/`trash`, plus three new files -- `apps/api/src/authz/project-role.guard.spec.ts` (7 cases), `apps/api/src/authz/permission.guard.spec.ts` (6 cases), and `apps/api/src/content/my-approvals.controller.spec.ts` (5 cases). The third pass closed out what the second pass's own scope note had left open: `content.service.spec.ts` grew another 12 cases covering `restore`, `remove`, and `getApprovalStatus`'s own `canAct`/history-shaping logic. Six spec files, 60 tests total, all run and passing (`npx vitest run` inside `apps/api`, exit code 0 -- not just written, actually executed and observed green).

**Why unit-level, with a hand-built fake Prisma, rather than an integration/e2e suite against a real database.** `apps/api` already has a Vitest e2e config (`vitest.config.e2e.ts`, matching `**/*.e2e-spec.ts`) that boots the real `AppModule` against a real Postgres/MySQL connection, but that connection only exists inside the running `docker-compose` network -- the `db` service deliberately has no host port mapping (see `docker-compose.yml`'s own comment: "the database is reachable only from `api`/`web` over the internal compose network... never from the host"). This development shell runs outside that network entirely (confirmed: `curl` to the app's own port from here returns connection-refused), so an e2e suite can't run here at all -- it would need to run inside the `api` container, which this shell has no exec access to. Vitest's unit tests, by contrast, transpile via esbuild rather than a full `tsc` type-check, so they run fine even with the environment's separate, unrelated stale-Prisma-client issue (the local `node_modules/.prisma/client` is missing several newer schema models, which blocks a clean `tsc --noEmit` on `apps/api` but doesn't block Vitest). Every Prisma-touching dependency in both suites is therefore a hand-built plain object (`{ modelHasRole: { findMany: vi.fn()... } }`, cast `as any`) rather than a real `PrismaClient` instance.

**A real obstacle this surfaced:** merely importing `RolesService` or `ContentService` in a test -- even when every constructor argument passed is a fake -- turned out to eagerly load the *real* Prisma query engine and crash with `PrismaClientInitializationError: ... generated for "darwin-arm64", but the actual deployment required "linux-arm64-openssl-3.0.x"`. Both classes carry `@Injectable()` and a constructor parameter typed `PrismaService`; with `emitDecoratorMetadata` on (required for Nest's DI), the compiled output has to reference the real `PrismaService` class as a runtime *value*, not just a type, for `design:paramtypes` -- and `PrismaService extends PrismaClient`, so merely loading that class attempts to load the query engine binary, which was generated on the developer's Mac (darwin-arm64) and doesn't match this shell's linux-arm64 host. This is the same pre-existing Prisma/host mismatch already noted elsewhere in this document (the blocked `prisma generate` re-fetch), surfacing through a new path -- not a defect in `RolesService`/`ContentService` themselves, and not fixable from here (regenerating with the right `binaryTargets` needs network access to `binaries.prisma.sh`, which is blocked in this environment). Worked around per-suite with `vi.mock('../prisma/prisma.service.js', () => ({ PrismaService: class {} }))`, which replaces the module before either class is imported; since `ContentService` depends on `RolesService` which depends on `PrismaService`, mocking `PrismaService` once is enough to keep the real broken class out of both suites' import chains. Confirmed this was necessary and sufficient: without the mock, `vitest run` reported the 11/8 tests themselves all green but exited with code 1 over the unhandled rejection; with it, the same tests pass with a clean exit 0.

**`roles.service.spec.ts` covers `RolesService.getUserRoles` and `RolesService.satisfiesRoleKind`** -- the one place every role-name string in `model_has_roles` becomes the structured `UserRoles` object every other authorization check in this codebase reads, so a silent regression here would silently misauthorize everywhere at once. Scenarios: direct project-tier grants (`editor{id}`, `viewer{id}`) parse correctly and never trigger the inherited-project expansion query; a `super_admin` grant short-circuits that expansion even alongside a `department_admin` grant; a Department Admin grant expands into `adminProjectIds` via the department-scoped project query without polluting `directAdminProjectIds`; a Tenant Admin grant expands the same way via the tenant-scoped filter; a project id held both directly and via expansion de-duplicates in `adminProjectIds` while `directAdminProjectIds` stays exactly the direct grant; a `custom_role{id}` grant resolves with its `permissions` JSON decoded. For `satisfiesRoleKind`: Super Admin passes every kind unconditionally; `'admin'` kind checks `directAdminProjectIds` specifically, not the inherited `adminProjectIds` (a Department Admin whose scope was merely expanded to include a project does *not* count as a direct Admin on it); `'department_admin'` kind has **no fallback to `tenantAdminTenantIds`** -- encoded here as an explicit regression guard after this document's own §11.8 write-up initially claimed such a hierarchy existed and had to be corrected once the actual code was re-read (a Tenant Admin alone does not satisfy a `department_admin`-kind step); `'tenant_admin'` kind checks `tenantAdminTenantIds` only; and every kind returns `false`, not throws, when its relevant context field is simply missing.

**`content.service.spec.ts` covers `ContentService.getPendingApprovalsForUser`** -- the query backing the §11.8 approvals bell. Scenarios: the Prisma `where` clause is asserted to be exactly `{ status: 'pending', content: { deletedAt: null } }`, a direct regression guard for the live ghost-notification bug §11.8 found and fixed; filtering is per-request rather than all-or-nothing (two pending requests with different `requiredRoleKind`/scope, a fake `satisfiesRoleKind` that approves only one, and the resulting list contains only that one -- with an explicit assertion that the *scope object* passed to `satisfiesRoleKind` for each request reflects that request's own project/department/tenant, not a shared or stale object); a request whose `currentStepOrder` no longer matches any step on its own workflow (e.g. the workflow's steps changed after submission) is silently skipped rather than surfaced or thrown; the title-resolution fallback chain matches `ContentService.list()`'s own convention exactly -- no title/name field present falls back to the collection's first field's actual value (not immediately `#<id>` -- a case this suite's first draft got wrong and had to fix after actually running it and reading the failure), and only when that resolved value is itself null/undefined/empty does the display fall back to `#<contentId>`; a populated title field is used as-is; and a project with no department produces `departmentId`/`tenantId` as `undefined` in the scope passed to `satisfiesRoleKind`, not a thrown error.

**`content.service.spec.ts`'s second pass covers `approveContent`, `rejectContent`, and `trash`** -- the actual write paths, where getting something wrong is a real authorization or data-integrity bug rather than a display glitch. Shared scenarios across both `approveContent`/`rejectContent`: content that doesn't exist (or is trashed) in the given project/collection throws `NotFoundException` before any approval-request lookup runs; no pending request for the content throws `NotFoundException`; a `currentStepOrder` that doesn't match any step on the workflow throws `NotFoundException` naming the missing step; and failing `satisfiesRoleKind` throws a `ForbiddenException` naming the required role kind, with no `ContentApprovalAction` row created and no transaction run. `approveContent` specifically: a non-final step records the approval and advances `currentStepOrder` by exactly one, without touching `$transaction` or `Content.publishedAt` at all (proving a mid-workflow approval can't accidentally publish); the true final step (`currentStepOrder >= steps.length`) instead runs a `$transaction` that both marks the request `'approved'` and sets `Content.publishedAt`/`publishedBy` -- the one moment this whole workflow exists to gate. `rejectContent`: an authorized rejection runs a `$transaction` that creates a `'rejected'` `ContentApprovalAction` and marks the *whole request* `'rejected'` (not just the current step), matching the "no partial credit on resubmission" design in this method's own comment. `trash`: content that doesn't exist throws `NotFoundException` and updates nothing; existing content gets both `Content.deletedAt` and every `ContentMeta.deletedAt` set to a real `Date` via `$transaction` -- a direct regression guard for the fact this exact `deletedAt` stamp is what `getPendingApprovalsForUser`'s `content: { deletedAt: null }` filter (§11.8's ghost-notification fix) actually depends on to exclude trashed content; if `trash()` ever stopped setting it, that filter would silently stop working too, and this test would catch it before that filter's own test would.

**`project-role.guard.spec.ts` and `permission.guard.spec.ts` cover the two guards nearly every admin route runs through.** Both share the same request-shape contract (documented in `require-project-role.decorator.ts`'s own comments) and both suites verify it identically: a route with no `@RequireProjectRole`/`@RequirePermission` metadata at all passes through untouched with zero calls to `RolesService` (the "route didn't opt in" fast path); an unauthenticated request (`request.user` missing) throws `ForbiddenException('Not authenticated')` before any role/permission resolution runs; a route with neither a `:projectId` nor an `:id` param throws `ForbiddenException('No project context for this route')`; and the project id is read from `:projectId` when present, falling back to `:id` for routes shaped like `ProjectsController`'s own (`DELETE /projects/:id`, etc.). `ProjectRoleGuard` additionally verifies: `canAccess`'s result gates the outcome directly (approve → `true` and `request.projectRoles` is set to the resolved roles object; deny → `ForbiddenException` naming both the required tier and the project id). `PermissionGuard` verifies the same shape for `getPermissionsForProjectId` and `request.permissions`, confirming this is genuinely a different code path (a `Set<Permission>` membership check) rather than an assumption that "looks similar" means "behaves the same."

**`my-approvals.controller.spec.ts` covers the one piece of logic `MyApprovalsController` owns itself** -- turning the JWT's `sub` claim into the numeric `userId` that `getPendingApprovalsForUser` is keyed on, via `Number(req.user?.sub) || 0`. Covered: a numeric-string `sub` and an already-numeric `sub` both resolve correctly; a request with no `user` at all, and a `sub` that isn't numeric, both fall back to `userId` 0 silently rather than throwing (matching the real `|| 0` behavior exactly, edge cases included); and the controller returns whatever `ContentService` resolves unmodified.

**`content.service.spec.ts`'s third pass covers `restore`, `remove`, and `getApprovalStatus`'s own logic** -- the items the second pass's scope note had explicitly deferred. `restore`: no trashed content matching the id throws `NotFoundException('Trashed content <id> not found')` with no transaction run; the lookup itself is asserted to require `deletedAt: { not: null }` -- restoring only makes sense for something actually in the trash; and a match clears `deletedAt` back to `null` on both `Content` and every `ContentMeta` row via `$transaction`. `remove`: content missing entirely throws `NotFoundException` and deletes nothing; the lookup is asserted to carry **no** `deletedAt` filter at all -- unlike every other lookup in this file, `remove()` must be able to find and hard-delete something that's already trashed, matching `mustExist(..., true)`'s `includeTrashed` argument; and a match runs a `$transaction` that hard-deletes the meta rows via `deleteMany` and then the content row itself via `delete` (not soft-deletes -- this is the one genuinely destructive path in `ContentService`).

`getApprovalStatus` is the one method in this file that reuses `satisfiesRoleKind` for a *display* decision (§11.3's original gap: hiding the Approve/Reject buttons for someone who can't act, rather than only erroring after a doomed click) rather than to gate a write, so its own `canAct` computation gets tested directly rather than assumed correct because the underlying role check already is. Covered: content missing (even when trashed -- confirmed the lookup carries no `deletedAt` filter, same reasoning as `remove()`, since status should stay readable for content trashed after submission) throws `NotFoundException`; no approval request ever submitted for the content returns `null` outright; a most-recent request that is no longer `'pending'` (e.g. `'approved'`) yields `canAct: false` **without even calling `getUserRoles`** -- proved by rigging `satisfiesRoleKind` to return `true` and confirming the result is still `false`, so the short-circuit is real and not a coincidence of the fake's default; the same short-circuit-without-a-roles-call holds when a `'pending'` request's `currentStepOrder` no longer matches any step on its workflow; a genuine pending-request-at-a-real-step case resolves `canAct` via `satisfiesRoleKind`, called with this project's own department/tenant scope (not a stale or shared one); and the returned shape -- `totalSteps`, per-step `{stepOrder, requiredRoleKind}`, and `history` mapped from `actions` in original order with `stepOrder`/`actorId`/`action`/`comment`/`createdAt` intact -- matches the method's own return statement field-for-field.

**Still not attempted in this pass, and why:** a real e2e run of the guards wired into actual NestJS request pipelines (`Test.createTestingModule` + supertest) rather than calling `canActivate` directly, and equivalent e2e coverage for the controllers/services generally -- both blocked by the same DB-unreachable-from-this-shell constraint noted throughout this section (the `db` service has no host port mapping; a real e2e suite needs to run inside the `api` container itself, which this shell cannot exec into directly). With this pass, unit-level coverage across `RolesService`, `ContentService`'s full approval/trash/restore/remove surface, both project-scoping guards, and `MyApprovalsController` is complete. **Update, §11.12: a real e2e suite has since been written** -- this shell still can't execute it against the real database, but it's ready for the user to run inside the `api` container, closing the gap this note originally flagged as blocked rather than leaving it open indefinitely.

### 11.10 Tenant Admin assignment screen (§11.1's deferred gap, closed)

§11.1 deferred Tenant Admin assignment as "still only one real Tenant, so this stays low-priority" once Department Admin assignment (§11.2's `DepartmentAdminsPanel.tsx`) had a real UI. Revisiting it, that reasoning held up the wrong thing: a single real Tenant is a reason the screen sees little traffic today, not a reason to leave the one tier below Super Admin with no assignment UI at all -- especially once Department Admin assignment already existed one tier down. Built this pass, mirroring §11.2's Department screen one tier up.

**Backend:** `apps/api/src/tenants/` (new module: `tenants.service.ts`, `.controller.ts`, `.module.ts`, registered in `app.module.ts`) -- `GET /tenants` (every Tenant the caller is Tenant Admin over, or all of them for a Super Admin -- same "no scope, no rows" empty-list default as `DepartmentsService.listVisibleDepartments`, not a 403), `GET /tenants/:id` (detail plus a `canManageAdmins` flag), `GET /tenants/:id/departments` (every Department in that Tenant), and `GET/POST/DELETE /tenants/:id/admins` (list/grant/revoke `tenant_admin{id}`, existing-account-only grants, matching every other role-grant path in this codebase).

**One deliberate design difference from Departments:** `DepartmentsService` splits viewing and managing into two separate checks (`canView`: Super Admin, Tenant Admin of its Tenant, or Department Admin of that exact Department; `canManageAdmins`: Tenant Admin/Super Admin only, narrower, so a Department Admin can see their own admin list but not add to it) because Department sits in the middle of the hierarchy, with a tier above it that should manage it and a tier at it that should only view it. Tenant is the topmost tier below Super Admin -- there's no tier above a Tenant Admin except Super Admin itself -- so `TenantsService` uses one `canAccess` check (`isSuperAdmin || tenantAdminTenantIds.includes(tenantId)`) for both viewing and managing: a Tenant Admin who can see a Tenant at all is, by construction, also the right tier to manage its admins.

**Frontend:** `apps/web/src/app/(dashboard)/tenants/` (new: `page.tsx` -- a Tenants list, one card per Tenant the signed-in user can see, mirroring `departments/page.tsx`'s shape and empty-state convention exactly; `[tenantId]/page.tsx` -- Tenant detail, listing its Departments (each linking into that Department's existing detail page) plus `TenantAdminsPanel.tsx`, a client component for granting/revoking Tenant Admin, read-only when `canManageAdmins` is false; `[tenantId]/actions.ts` -- the same local `apiFetch`/`revalidatePath` server-action shape every other feature folder in this codebase keeps). Added a "Tenants" entry to the global nav (`TopNav.tsx`, desktop and mobile), alongside the existing "Departments" link.

**One deliberate addition beyond a straight Departments mirror:** `TenantAdminsPanel.tsx` hides both the impersonate button and the revoke button (with a "(you)" label instead) on the signed-in user's own row, via `admin.email === session?.user?.email`. Department Admin is managed by the tier above it (Tenant Admin), so a Department Admin can never encounter their own row in that panel's admin list in the first place -- self-revoke structurally can't happen there. Tenant Admin has no tier above it except Super Admin, and is managed by Tenant Admins themselves, so without this guard a lone Tenant Admin could revoke their own access by a misclick. Super Admin can always re-grant it, so this is a UI safety net against that misclick, not a backend restriction: `TenantsService.revokeTenantAdmin` itself still permits self-revoke, matching this codebase's consistent convention of keeping authorization logic server-side only and never duplicating it as a client-side-only rule.

`docker/nginx/gateway.conf` got the same treatment as `/departments` in §11.2, for the same reason: `/tenants` is both a Next.js dashboard page and an api-side `@Controller('tenants')`, so it deliberately gets no gateway `location` block -- a comment was added explaining this and pointing at `docker compose exec api curl http://localhost:4000/tenants/...` as the way to test these routes directly, rather than repeating the mistake §11.2 had to fix (a gateway block that hijacked the dashboard page itself).

**Typecheck:** both `apps/api/tsconfig.json` and `apps/web/tsconfig.json` were checked for every new/changed file here. `web`'s `tsc --noEmit` exits 0 outright. `api` shows only the same four pre-existing stale-Prisma-client-category errors already flagged throughout this document (cross-referenced against `departments.service.ts`'s own identical error shapes to confirm these are the same known issue, not a new one this module introduced).

### 11.12 A real e2e suite, against the real database (§11.9/§11.11's flagged gap)

§11.9 and §11.11 both named the same standing gap: every automated test in this document up to here fakes `PrismaService` to avoid the darwin/linux Prisma engine mismatch (§11.9's own write-up), which proves the authorization *logic* is correct but never proves it's wired correctly into a real, running NestJS app talking to the real MySQL database. This section closes that gap with `apps/api/test/rbac.e2e-spec.ts`, a new `*.e2e-spec.ts` file using the `vitest.config.e2e.ts` config and `test:e2e` script that already existed in this repo but had only ever run the one pre-existing `AppController` smoke test (§11.9's own explanation of why: `apps/api`'s e2e config boots the real `AppModule`, and the `db` compose service has no host port mapping, so it's only reachable from inside the compose network).

**What it does, and deliberately does not fake:** it boots the real `AppModule` via `Test.createTestingModule`, pulls the real `JwtService` and `PrismaService` out of that module's DI container, looks up the four established test users (`admin@veroxm.com`, `dept-admin@example.test`, `dept-editor@example.test`, `plain-editor@example.test`) by email through the real database, and mints real HS256 API tokens for each with `jwt.sign({ sub: user.id, email: user.email }, ...)` -- the exact payload shape and signing call `apps/web/src/lib/auth.ts`'s own NextAuth `jwt` callback uses to mint `session.apiToken`, not a stand-in. It then drives real HTTP requests at the real `JwtAuthGuard`/`ProjectRoleGuard`/`PermissionGuard`/controller stack via supertest, the same way a real browser session does, and asserts on the real JSON responses. Ten cases: two authentication rejections (no token, garbage token); four on `GET /tenants` covering Super Admin, a Department-Admin-only user, a genuine Tenant Admin, and a user with no elevated access at all; two on `GET /departments`; and two on `GET /permissions/my-permissions/:projectId`, one proving an Admin-or-above grant includes `content:approve` and one proving `plain-editor@example.test`'s bundle excludes every Admin-tier permission -- see the real finding below for why that second assertion isn't quite "no `content:approve`" the way its first draft assumed.

**Looks up users and the target project by name/email rather than hardcoding ids**, so the suite keeps working if the seed data is ever reloaded with different auto-increment ids, and fails fast with a named error (which seeded email or project is missing) rather than a confusing assertion failure deep in a test body if the seed hasn't been applied yet.

**Verified so far, honestly, and no further:** run from this shell (not inside the `api` container, since this shell has no route into the compose network -- the same limitation §11.9 and §11.11 both already named), `npx vitest run --config ./vitest.config.e2e.ts` inside `apps/api` correctly discovers and attempts all 10 new cases, then fails all of them on the expected `PrismaClientInitializationError: ... generated for "darwin-arm64", but the actual deployment required "linux-arm64-openssl-3.0.x"` -- the same root cause blocking a clean `tsc --noEmit` on `apps/api` throughout §11, now hit for real instead of mocked around, since this file deliberately does not mock `PrismaService`. This confirms the suite is structurally sound and gets as far as actually calling the real `PrismaService` -- it does **not** confirm the suite passes against a real database, because this shell cannot reach one. `npx tsc --noEmit` shows exactly one error for this new file, `Cannot find module 'supertest/types'` -- the identical pre-existing error the original `app.e2e-spec.ts` already had, not a new category this file introduces.

**To actually run it, from your machine:** in this npm-workspaces monorepo, `docker compose exec api npm run test:e2e` alone fails with `Missing script: "test:e2e"` -- the root `package.json` has no such script (only `apps/api/package.json` does), unlike `db:generate`, which the root package.json explicitly delegates via `--workspace=packages/db`. The correct invocation, confirmed working: `docker compose exec api npm run test:e2e --workspace=apps/api`. Worth remembering alongside this repo's other npm-workspaces gotcha (§11's own `db:generate` note) rather than rediscovering it next time.

**Run for real, against the real stack, and it found something real.** First run: 10 of 11 tests passed (including the pre-existing `AppController` smoke test); one failed --  `plain-editor@example.test`'s permission bundle on "Slice 1 Test Project A" unexpectedly included `content:approve`, which this suite had asserted should be absent. Checked live via the dashboard (`/departments/1`'s Custom Roles panel) rather than guessed at: `plain-editor@example.test` turned out to already hold a **"Content Approver" custom role** (`content:read` + `content:approve` only) scoped to Nami Test Department -- a real, left-in-place grant from this engagement's own earlier custom-roles testing (§11's implementation-status section), not a bug and not test-environment corruption. §5.7 explicitly designed for one user holding multiple roles across scopes at once, and a narrow custom role granting `content:approve` to a non-admin is exactly what §5.6 built custom roles to do -- so the permission-service behavior was correct throughout; this suite's own first-draft assumption that `plain-editor@example.test` was a "zero elevated access" account with nothing but its direct `editor{id}` grant was simply stale, since this engagement's own testing had, at some point, used that account to exercise the custom-roles feature and never revoked the grant.

**Fixed by correcting the test, not the code:** the assertion was changed from "no `content:approve`" to "no `members:manage`/`workflow:configure`/`roles:configure`" -- the three permissions that are genuinely Admin/Department Admin/Tenant Admin exclusives and that this specific custom role doesn't grant, making them the actually-reliable signal that a user isn't some tier of Admin, regardless of what narrower custom roles get layered on afterward. **Re-run against the real stack after the fix, by the user, from their machine: all green.** `docker compose exec api npm run test:e2e --workspace=apps/api` -- `Test Files 2 passed (2)`, `Tests 11 passed (11)` (the pre-existing `AppController` smoke test plus all 10 of this suite's own cases). This is a real result, actually observed, not inferred from the structural check alone.

This is the concrete payoff §11.9/§11.11 predicted for closing this gap: a fake-`PrismaService` unit test can never catch drift in real seed data (there's no real data to drift), and this one did, on its very first real run.

**Cleaned up the actual drift, not just the test.** Revoked `plain-editor@example.test`'s leftover "Content Approver" custom-role grant from `/departments/1`'s Custom Roles panel (confirmed live: the row disappeared from that role's grantee list after the delete resolved, the same real-fetch confirmation standard used throughout this document, not just an optimistic client-side update). `plain-editor@example.test` is once again a genuine zero-elevated-access account, matching how it's described everywhere else in this document -- the corrected test assertion (checking for absent Admin-tier permissions rather than absent `content:approve` specifically) was kept as-is rather than reverted, since it's the more robust check either way and doesn't assume no custom role will ever be granted to this account again.

### 11.13 A real privilege-escalation bug, found by an adversarial review and fixed

With §11.12 giving this document real automated coverage against the live stack, the next step was an independent adversarial security review of the whole authorization surface built across §11 -- not testing the scenarios I already had in mind (which is all every other test in this document does), but a fresh pass specifically hunting for exploitable gaps. One real, confirmed bug came out of it.

**The bug.** `ApprovalWorkflowsService.canConfigure` (the check gating a Department's own approval workflow) deliberately excludes Department Admin -- its own comment says why: *"a Department Admin shouldn't be able to loosen or remove the approval gate governing their own department."* Only a Tenant Admin (or Super Admin) can configure a Department's workflow, for exactly that reason. But `canManageProjectOverride` (§11.6, the Project-level override that **fully replaces** a Department's workflow for one project) used the *same* check for both viewing AND configuring, and that check *did* include Department Admin -- §11.6's own write-up justified this as "the same authority that already configures the Department's own workflow," which is simply false; `canConfigure` proves Department Admin never had that authority at the department level. Combined with the fact that `POST /projects/:projectId/members` (role-management, §11.1) lets anyone holding `members:manage` -- which every Department Admin holds on every project in their department -- grant a role to **any** email including their own, the full chain was: a Department Admin sets a project's override to a single `admin`-tier step, grants themselves a direct `admin{projectId}` role, and approves their own content -- completely bypassing whatever stricter workflow (say, one requiring Tenant Admin sign-off for compliance reasons) a Tenant Admin had configured for that Department. A single Department Admin, acting alone, with tools this document had already built for other reasons, fully defeating the separation-of-duties the workflow feature exists to provide.

**The fix.** Split the single check into two, mirroring the Department-level pattern exactly: `canViewProjectOverride` (Super Admin, Tenant Admin, or Department Admin -- unchanged, so a Department Admin can still see why a publish is gated) and a new, stricter `canManageProjectOverride` (Super Admin or Tenant Admin of the project's department's tenant **only** -- Department Admin removed). `getProjectWorkflow` now returns `{ canManage, workflow }` instead of a bare `ProjectApprovalWorkflowDto | null`, since a bare `null` can't carry the extra bit a Department Admin's read-only view needs; `setProjectSteps`/`removeProjectWorkflow` now gate on the strict check, with their `ForbiddenException` messages updated to no longer name Department Admin as allowed. On the frontend, `ProjectApprovalWorkflowPanel.tsx` gained the same `canManage`-gated read-only rendering the Department-level `ApprovalWorkflowPanel.tsx` already had (steps shown as plain text instead of a dropdown, Add/Save/Remove controls hidden, a one-line explanation of why) -- built by directly mirroring that existing, already-correct pattern rather than inventing a new one.

**Verified clean, then verified live.** `npx tsc --noEmit`: `apps/web` exits 0; `apps/api` shows no new error category, only the same pre-existing stale-Prisma-client errors already documented throughout §11 (confirmed by grepping the output for this module's own file specifically). `npx vitest run`: all 60 existing unit tests still pass unchanged (this module has no dedicated unit spec of its own, consistent with the other feature modules §11.9 notes as untested at the unit level). Then, after the user restarted `api`/`web` to pick up the change, verified live through the browser on Project 17 ("Slice 1 Test Project A," which already had a project-level override from §11.6's own testing): as Super Admin, the panel still shows full edit controls; impersonating `dept-admin@example.test` (Department Admin, holding `department_admin1` -- no Tenant Admin grant), the panel now shows the step as read-only text ("Department Admin approves"), no Add step/Save/Remove controls, and the new explanatory line ("Only a Tenant Admin (or Super Admin) can change this override — you can see it, but not edit it"); impersonating `dept-editor@example.test` (holds `tenant_admin1`, the control-group check), the panel still shows full edit controls, exactly as before -- confirming the fix removed Department Admin's access specifically, without touching Tenant Admin's.

**What this doesn't fix, and is worth naming rather than leaving implicit.** The underlying self-grant path -- `POST /projects/:projectId/members` letting a `members:manage` holder grant a role to their own email with no restriction -- still exists, and is a real (if narrower) design question in its own right: should any admin-tier user ever be allowed to grant a role to themselves through that endpoint? This fix closes the specific chain that made it a genuine separation-of-duties bypass (a Department Admin can no longer weaken the gate that self-grant would otherwise let them walk through), but the self-grant capability itself is unchanged and is flagged here as a real, distinct follow-up worth a deliberate decision rather than default behavior nobody chose on purpose.

This is the second concrete payoff this document has gotten from actually looking rather than assuming: §11.12 caught real seed-data drift with an automated test; this section caught a real, exploitable authorization bug with an adversarial review -- both only became possible once there was enough built to review.

### 11.14 Tenant-level CRUD (create, rename, delete)

Tenant management until now (§11.10) covered only viewing a Tenant and granting/revoking Tenant Admin on it -- the Tenant *record itself* (its name, its existence) could only be created or removed directly in the database. This closes that gap: `POST /tenants`, `PATCH /tenants/:tenantId`, and `DELETE /tenants/:tenantId`, plus the frontend to drive them.

**Permission split, not one flag.** A bare `canManageAdmins` boolean already existed on `TenantDetail`; this adds two more rather than overloading it, matching this file's own established discipline (see §11.13's `canViewProjectOverride`/`canManageProjectOverride` split) of keeping conceptually different questions as separate fields even where they coincide today:
- **`canCreate`** (on the list response) -- Super Admin only. There's no tier between Tenant Admin and Super Admin the way there is between Department Admin and Tenant Admin, and creating a Tenant establishes a brand-new top-level boundary -- there's no existing Tenant to be "Tenant Admin of" yet, so this can't be delegated the way renaming or admin-management can.
- **`canEditDetails`** -- Super Admin, or Tenant Admin of that specific Tenant (identical to the existing `canAccess` check). Renaming a Tenant you already administer is low-risk and reversible, the same tier of action as managing its admin roster.
- **`canDelete`** -- Super Admin only. Deleting a Tenant is a one-way structural change (every Department, Project, and role grant beneath it loses its home) -- a step above what a single Tenant Admin should be able to do to their own tenant alone, the same reasoning §11.13 used to keep a Department Admin from weakening their own Department's approval gate.

**Slug is immutable.** The create form is the only place a slug is ever set. `updateTenant` only ever takes a `name` -- there's no route that changes a slug once a Tenant exists, because a slug is a stable identifier a future integration (a Keycloak Organization alias, per `IDENTITY-PLATFORM-RECOMMENDATION.md` §7) could come to depend on; changing it out from under such a reference would have no upside a rename doesn't already provide.

**Delete blocks rather than cascades, and says why.** `departments.tenant_id` (`packages/db/sql/0006_create_tenants.sql`) is a plain FK with no `ON DELETE` clause, which MySQL/InnoDB defaults to `RESTRICT`. Without a guard, deleting a Tenant that still has Departments would surface a raw SQL 1451 error through the API. `deleteTenant` counts Departments first and throws a `ConflictException` with an actionable message instead -- confirmed live against the real `VeroXM` tenant (which has one real Department, `Nami Test Department`): the delete was refused, `VeroXM` and its Department were untouched, and the panel showed *"Cannot delete this tenant: 1 department still belongs to it. Reassign or remove it first."* A Tenant that's actually empty deletes cleanly -- also confirmed live (see below). Deleting also cleans up the Tenant's own `tenant_admin{id}` Role row and any lingering grants of it, unlike `revokeTenantAdmin`, which deliberately leaves the Role in place for future re-grants -- here there's no "future" for a Tenant that no longer exists.

**A small bug this document's own discipline caught.** The first draft of that error message read *"Cannot delete this tenant: 1 department still belong to it"* -- correct for the plural case, wrong verb agreement for the singular one. Live-tested against `VeroXM` (a genuine 1-department case) rather than only read back as code, the mismatch was visible immediately. Fixed to conjugate the verb and pronoun (`belongs`/`belong`, `it`/`them`) alongside the noun, re-verified live after the fix -- the same "run it for real, don't just trust the diff" habit this document has followed since §11.12.

**Verified, in order:** `npx tsc --noEmit` on both apps -- `apps/web` exits 0; `apps/api` shows no new error category, only the same pre-existing stale-Prisma-client errors already documented throughout §11 (this dev shell can't regenerate the Prisma client at all here -- `prisma generate` fails fetching its engine binary from this network -- so this is read the same way every prior section has read it: pre-existing and repo-wide, not something this change introduced, confirmed by every other untouched service file showing the identical `Property '<model>' does not exist on type 'PrismaService'` shape). `npx vitest run` -- all 60 existing unit tests still pass unchanged. Then live, in the browser, as Super Admin: created a real Tenant ("CRUD Test Co" / `crud-test-co`), confirmed it appeared in the list via a real page reload (not optimistic client state); renamed it ("CRUD Test Co (Renamed)") and confirmed the new name persisted through a fresh server fetch, with the slug staying fixed; attempted to create a second Tenant with the already-used slug `veroxm` and got the clean `Slug "veroxm" is already in use by another tenant` rejection, with nothing created; deleted the empty test Tenant and confirmed it was gone from a freshly-fetched list. Then impersonated `dept-editor@example.test` (holds `tenant_admin1`, no Super Admin) and confirmed the permission split renders correctly: no "New tenant" control on the list page (`canCreate: false`), "Edit name" still available on `VeroXM`'s own detail page (`canEditDetails: true`), and the entire "Delete tenant" section -- button, confirm step, and explanatory copy -- absent rather than merely disabled (`canDelete: false`).

This closes the last item on the "explicitly deprioritized" list from earlier in this engagement -- Tenant-level CRUD -- the same way §11.10-§11.13 closed the others: read the existing code and conventions first, mirror them rather than inventing new ones (the envelope-response pattern, the view/manage permission split, the department-count-before-delete guard), and verify every claim live against the real stack rather than trusting the diff.

### 11.15 The self-grant question, closed narrowly

§11.13 fixed a real privilege-escalation chain but deliberately left one piece of it named and unaddressed: `RoleManagementService.assignProjectRole` (`POST /projects/:projectId/members`, gated on `members:manage`) let a caller grant *any* project role kind to *any* email, including their own. Every Department Admin, Tenant Admin, and Super Admin holds `members:manage` on every project in their scope -- §11.13's fix closed the specific route that made that a workflow-bypassing exploit, but the bare capability to self-grant was flagged as "a real, distinct design question" rather than fixed. This closes it.

**What self-granting actually changes -- traced, not assumed.** Not every project role kind is equally interesting to self-grant. `ROLE_PERMISSIONS` (`apps/api/src/authz/permissions.ts`) gives `admin` (the project tier) no `members:manage` of its own -- only `department_admin`/`tenant_admin`/`super_admin` carry it, and both of those already have broader, *inherited* effective access to every project in their scope (`adminProjectIds`). So what does directly self-granting `admin{projectId}` actually add for someone who already has all that? One thing, traced to a single call site: `RolesService.satisfiesRoleKind`'s `'admin'` branch deliberately checks `directAdminProjectIds`, never the inherited `adminProjectIds` superset -- its own comment explains why (an `'admin'`-tier approval-workflow step should require a real, direct grant, not just "anyone with admin-level reach via inheritance"). `directAdminProjectIds` has exactly one consumer in this codebase (confirmed by grep, not assumption): that check. So self-granting `admin` is the one project role kind that changes real capability -- it lets a Department/Tenant Admin satisfy an `'admin'`-tier approval step (§6, §11.13) they would not otherwise satisfy through their inherited access alone. Self-granting `editor`/`developer`/`viewer` has no equivalent effect: nothing checks those kinds via a direct-only path, so at most it's redundant with access the caller already has -- never a new capability.

**The fix, sized to match.** `assignProjectRole` now takes the caller's own `userId` (threaded through from `JwtAuthGuard` in the controller, which didn't even read `@Req()` before this) and rejects `roleKind === 'admin'` when the target email resolves to the caller's own account, before any read or write touches the database -- `"You can't grant yourself the Admin role on a project -- ask another Admin, Department Admin, Tenant Admin, or Super Admin to grant it."` Self-granting `editor`/`developer`/`viewer` is left untouched: blocking those would be pure friction with no protective benefit, given the trace above. This is deliberately narrower than blocking all self-grants outright -- the narrower fix is the one actually justified by what the code does, not the more sweeping one that would have been easier to justify by intuition alone.

**Verified, in order.** Added `role-management.service.spec.ts` -- this module's first dedicated unit coverage -- with five cases: self-granting `admin` is rejected with no database write attempted; self-granting each of `editor`/`developer`/`viewer` still succeeds; granting `admin` to someone other than the caller still succeeds; the pre-existing invalid-roleKind and no-such-user checks still fire first, ahead of the new guard. `npx tsc --noEmit` clean on the controller and both new/changed files; `npx vitest run` -- 67 of 67 (60 existing + 7 new) passing. Then live, impersonating `dept-admin@example.test` (Department Admin, holding `department_admin1` -- no Tenant Admin, no pre-existing direct grant beyond what the test itself created) on `Slice 1 Test Project A`: attempting to grant themselves Admin was refused with the exact message above and no new row appeared; granting themselves Viewer succeeded and a new row appeared (then revoked, to leave the project's real membership as found); granting Admin to `dept-editor@example.test` (a different user) still succeeded (then revoked the same way). Confirmed via the Tenants screen that `dept-editor@example.test`'s real `tenant_admin1` grant was untouched by any of this -- the guard only ever touches project-level role rows, never the Tenant/Department role model the inherited-access checks read from.

This closes every item this engagement's own §11.13 named as still open. ~~What remains is genuinely outside this document's authority to decide alone: the three business/policy questions flagged earlier in this engagement, none of which this document invents an answer for.~~ **Update:** those three business/policy questions were walked through with the user and resolved directly in §10 shortly after this section was written — two with real decisions (on-prem update model, on-prem licensing) and one resolved as an explicit, deliberate deferral (custom-role tiering), not left open by default. What remains genuinely open, and still outside this document's authority to decide alone, is narrower than this section originally said: only the contract-value realm-threshold override flagged in §10's first bullet, which still awaits real SaaS customer data to calibrate against.
